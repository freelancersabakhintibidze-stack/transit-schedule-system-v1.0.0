About the system

Schedule Notes

What this system publishes, how it is built, and where its boundaries are. Everything on this page describes the application exactly as it is.

01 Purpose

Meridian Transit is a public schedule information system for the fictional Meridian network. It lets passengers discover routes by number, transport type, origin, or destination; inspect the ordered stop sequence of any route; and query any stop to see every active route serving it together with its upcoming departures. The interface is built for quick, repeatable lookups rather than trip planning, and every screen presents the same three controls consistently: a search or selection, a transport or day filter, and a reference time.

The system runs entirely on a static, normalised dataset. That is a deliberate choice for this release: it keeps the application honest about what it knows, makes it fully reproducible in tests, and leaves the repository interface unchanged when a real schedule API is introduced later.

02 Planned timetables, not live tracking

Every departure time shown in this system is a published planned timetable entry. The application does not ingest vehicle positions, does not estimate delays, and does not predict arrivals. A departure listed at 08:12 is the time the operator has scheduled, not a guarantee that a vehicle will leave at that second.

The "next departure" readout is computed from your selected reference time and the planned timetable only. If the day's service has ended, the system states that plainly instead of showing an optimistic countdown. This distinction between schedule and reality is repeated on the timetable screens because it is the most important thing a schedule product must communicate truthfully.

03 How the data is organized

The dataset is strictly normalised into four entities, managed independently of one another:

  • Route: number, transport type, origin and destination, and an active flag.
  • Stop: name and address, identified by a stable numeric id.
  • RouteStop: the join between routes and stops, with a sequence number that strictly dictates ordering.
  • Departure: one planned time for a route on a day type.

Route numbers are display labels and are never used as primary identifiers, so a future renumbering campaign cannot corrupt references. Day types are WEEKDAY, SATURDAY, and SUNDAY_HOLIDAY. All comparisons are performed on minutes from midnight rather than on time strings, and every dataset is validated and deep frozen before the application reads it.

04 How the next departure is computed

Given a route, a day type, and your reference time, the engine converts all departure strings of that route and day into minutes from midnight, sorts them once, and performs a binary search for the first departure at or after the reference time. Exact matches are returned as-is. When every departure has passed, the engine returns an explicit end of service state and the interface displays it verbatim. Malformed times are filtered out during validation and can never reach the comparison.

The reference time defaults to your device clock and refreshes as the clock advances until you set a time yourself, which keeps the readout honest without any background polling of vehicle data.

05 Accessibility, performance, and privacy

The interface uses semantic tables and lists, visible focus states, aria-pressed segmented controls, a skip link, and colour contrast that meets WCAG AA for text. Filtering and search are computed synchronously over indexed data; the search and departure engine is exercised in unit tests against a synthetic 500-route network. The application collects no personal information, sets no cookies, and performs no telemetry; the only external requests it makes are the typefaces loaded from Google Fonts, which are disclosed in the privacy policy.
